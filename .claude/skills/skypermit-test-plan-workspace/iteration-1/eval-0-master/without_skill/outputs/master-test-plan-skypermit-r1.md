## 1. Мета

Описати **весь обсяг мануального тестування** SkyPermit перед першим релізом: що тестуємо, на якому рівні, з якими даними, у якому порядку пріоритетів, що зараз заблоковане відкритими питаннями та за яких умов реліз можна вважати готовим.

План не містить самих тест-кейсів. Він задає області тестування (`TA-xx`), ключові матриці й межові значення, з яких потім генеруються детальні тест-кейси в `test-cases/`.

| Що | Чому |

## 4. Підхід

### 4.1 Рівні і типи тестування

| Тип | Як | Інструмент |
|---|---|---|
| API functional | ручні запити до `/api/v1` | REST-клієнт (Postman/Insomnia/curl) |
| UI functional / E2E | сценарії в браузері через обидва портали | браузер + DevTools (Network) |
| Data verification | перевірка `ReviewAction`, `AuditLog`, збережених полів заявки | read-only доступ до БД **тестового** середовища |
| Contract checks | статус-коди, поля `422`, наявність `data-testid` | API-клієнт, DevTools |
| Negative / boundary | межові значення з розділу 6 | API (точні значення), UI (вибірково) |
| Smoke | 1 наскрізний «щасливий» шлях + по одному провалу кожного гейта | API + UI |
| Regression | повтор P1 після кожного фіксу | API + UI |

### 4.2 Техніки тест-дизайну

- **State transition testing:** повна матриця «стан × дія» (розділ 6.1), 7×5 комірок.
- **Decision tables:** рейтинг × клас зони, вагова категорія × `permitted_bands`, рівень авторизації × вимога зони.
- **Boundary value analysis:** межі ваги, висоти, тривалості, lead time, advance booking, currency, curfew, дедлайн скасування, довжина `flight_purpose`.
- **Pairwise / combination:** кілька гейтів провалюються одночасно → має повертатися лише перший за порядком.
- **Equivalence partitioning:** зони з комендантською годиною і без неї; зони з поправкою `A-7` і без неї.

### 4.3 Пріоритети

| Пріоритет | Що це |
|---|---|
| **P1** | блокує реліз: гейти, стан-машина, авторизація/ізоляція даних операторів, контракт `422`, `validate` без побічних ефектів |
| **P2** | важливо: фільтри, списки, UI-відображення причин відмови, аудит, похідні значення |
| **P3** | бажано: `data-testid` на всіх елементах, тексти повідомлень, дрібні негативні сценарії |

### 4.4 Робота з часом

Гейт `TIME_WINDOW` і дедлайн скасування залежать від поточного часу сервера. Docs не описують способу підмінити час, тому:

- вікна задаються **відносно поточного UTC-часу** у момент виконання (напр. `now + 6h 05m`);
- для межових значень (рівно 6 год, рівно 60 днів, рівно 2 год до старту) потрібен запас на час виконання кроку. Точну межу «секунда в секунду» мануально не перевірити, це обмеження фіксується в звіті;
- curfew задається в **місцевому часі зони**, а вікна передаються в UTC. Перетворення робить тестувальник (див. питання Q-06 про часовий пояс зони).

Кількість тест-кейсів наведено як орієнтир для планування, а не як фіксоване зобов'язання.

### TA-02. Авторизація та ізоляція даних — P1

| # | Що перевіряємо | Очікуване |
|---|---|---|
| 1 | Operator-scoped ендпоінти без сесії і без reviewer-хедера | `401` |
| 2 | Оператор A читає/змінює ресурс оператора B (pilot, aircraft, operator, flight-request get/submit/cancel/validate) | `403` |
| 3 | `operator_id` у тілі/query create-запитів ігнорується; власник береться із сесії | `03` Enforcement |
| 4 | Reviewer (`X-Reviewer-Id`) без сесії робить `GET` будь-якого pilot/aircraft/operator/flight-request і `validate` | дозволено |

| 6 | `GET /flight-requests` без хедера показує лише заявки оператора сесії; з хедером — усіх операторів + фільтр `operator_id` | `03` endpoint 12 |

Орієнтовно: 25–30 ТК (матриця «ендпоінт × тип викликача»: anonymous / owner / other operator / reviewer).

### TA-03. Реєстр пілотів — P1/P2

Джерела: `01` Pilot; `03` endpoints 3, 4, `GET /pilots`; `06` §2.

- Створення пілота під оператором сесії; `national_id` унікальний.
- Усі значення `rating`: `R_BASIC`, `R_ADVANCED`, `R_BVLOS`; невалідне значення → `400`.
- `GET /pilots/{id}` і `GET /pilots` повертають **похідний** статус currency (`01` Derived).
- Currency рахується від `certified_on` + 18 місяців (`06` §2). Регресія: 24 місяці (`OH-1` v1.4) **не** застосовуються.
- UI: сторінка реєстру пілотів зі списком і формою створення (`04`).
- `Pilot.status` не впливає на жоден гейт (`05` row 2) → пілот `INACTIVE` проходить `PILOT`-гейт, якщо рейтинг і currency валідні. Статус ставиться тільки out-of-band.

Орієнтовно: 12–15 ТК.

### TA-04. Реєстр повітряних суден і вагові категорії — P1

Джерела: `01` Aircraft, Derived; `06` §1.2, §3; `03` endpoints 5, 6.

- Створення ПС; `serial_number` унікальний.
- Похідна `weight band` у `GET /aircraft/{id}` і `GET /aircraft` за межами з розділу 6.3.
- `mtom_grams` > 30 000 → `422` на `POST /aircraft`, citation `OH-1 §3`, запис ПС не створюється (`06` §3). Форма тіла `422` без гейта не визначена → **Q-08**.
- Регресія: межа C1/C2 = 3 500 г, а не 4 000 г (`OH-1` v1.4); категорій `C4`/`C5` немає.
- `Aircraft.status = RETIRED` не впливає на гейти (`05` row 2).
- Перерахунок категорії при виправленні маси (`01` Derived) → **BLOCKED**: у контракті немає ендпоінта оновлення ПС (**Q-07**).

Орієнтовно: 15–18 ТК.

### TA-05. Довідник зон — P2

Джерела: `01` Zone; `03` endpoints 7, 8; `06` §4.

- `GET /zones` повертає рівно 6 зон, і всі атрибути збігаються з `06` §4 (клас, стеля, permitted bands, curfew з урахуванням `A-7`, рівень авторизації, `active`).
- Для `KBP-CTR-3` і `ODS-CTR-5` curfew = 23:00–05:00 (`A-7`), а не 22:00–06:00.
- `GET /zones/{code}` для неіснуючого коду → `404`.
- У API немає ендпоінтів create/update/delete для зон, в UI немає відповідної форми.
- Zone picker на формі заявки заповнюється з `GET /zones`.

Орієнтовно: 8–10 ТК.

### TA-06. Створення заявки (DRAFT) і форма — P1

Джерела: `01` FlightRequest, Time handling; `03` endpoint 9; `04` Request creation form.

- Створення заявки → стан `DRAFT`, гейти не запускаються (`02` States).
- Поля форми: zone, pilot, aircraft, window start/end, altitude, purpose (`04`).
- Pilot і aircraft pickers показують лише ресурси поточного оператора.
- **Форма не фільтрує за бізнес-правилами:** можна вибрати комбінацію, яка гарантовано не пройде (напр. `R_BASIC` + `LVV-RST-2`), і створити DRAFT (`04` «The form does not pre-filter»).
- `flight_purpose`: 2 000 символів приймається; 2 001 відхиляється і в API, і на рівні БД (`01` Time handling). Код відповіді → **Q-13**.
- Час зберігається в UTC; перевірити, що значення, введені в UI, коректно потрапляють в UTC (**Q-14**: часовий пояс полів UI не описаний).
- `window_end <= window_start` на створенні → **Q-15** (помилка create чи `TIME_WINDOW` на submit).
- Створення з чужим pilot/aircraft → очікується `403` (`03` Enforcement). Варто підтвердити (**Q-11**).

Орієнтовно: 15–20 ТК.

### TA-07. Гейт `PILOT` — P1

Джерела: `06` §1.1, §2, §6.

| Умова | Перевірка | `rule_reference` |
|---|---|---|
| Рейтинг × клас зони | матриця 6.2 (3 рейтинги × 3 класи) | `OH-1 §2.1` |
| Currency | 18 міс. від `certified_on`, перевіряється на `window_start`, а не на час сабміту | `OH-1 §2.3` |
| Currency lapse | сертифікат чинний на момент submit, але спливає до `window_start` → FAIL | `OH-1 §2.3` |

Орієнтовно: 14–16 ТК.

### TA-08. Гейт `AIRCRAFT` — P1

Джерела: `06` §1.2, §3; `07` п. 1.

- Вагова категорія ПС ∈ `permitted_bands` зони; провал → `failing_gate: AIRCRAFT`, **не** `ZONE` (`07` п. 1). Це ключова регресійна перевірка корекції корпусу.
- `rule_reference: "ZC-2026.1 §2"` (той самий, що й для висоти в `ZONE`; розрізняємо за `failing_gate`).
- Матриця 6.3 (межові маси × зони).
- `RETIRED` ПС не провалює гейт.

Орієнтовно: 12–14 ТК.

### TA-09. Гейт `ZONE` — P1

Джерела: `06` §1.3, §4, §6; `05` row 3, 5; `07` п. 4.

| Умова | Перевірка | `rule_reference` |
|---|---|---|
| Висота ≤ стелі | стеля і стеля + 1 для кожного значення стелі (120, 90, 60, 45) | `ZC-2026.1 §2` |
| Рівень авторизації оператора ≥ вимоги зони | матриця 6.4 | `OH-1 §4` |
| Зона неактивна | заявка на неактивну зону → FAIL `ZONE` | `ZC-2026.1 §4` — **NEEDS-CLARIFICATION** (`05` row 5, §2) |

Для неактивної зони потрібна підготовка даних поза продуктом: усі 6 зон активні за каталогом. Перевіряємо `failing_gate: ZONE` і сам факт відмови; значення `rule_reference` позначаємо як неостаточне.

Орієнтовно: 14–16 ТК.

### TA-10. Гейт `TIME_WINDOW` — P1

Джерела: `06` §1.4, §6; `01` Time handling; `02` Aircraft schedule overlap.

| Умова | Межі | `rule_reference` |
|---|---|---|
| Lead time | ≥ 6 год між сабмітом і `window_start` | `TSD-4 §2.1` |
| Advance booking | ≤ 60 днів до `window_start` | `TSD-4 §2.2` |
| Тривалість | 15–240 хв включно; `window_end` строго після `window_start` | `TSD-4 §3` |
| Curfew (`KBP-CTR-3`, `ODS-CTR-5`) | 23:00–05:00 місцевого часу | `A-7 §1` |
| Curfew (`LVV-RST-2`, `ZTM-RST-7`) | 22:00–06:00 місцевого часу | `ZC-2026.1 §3` |
| Без curfew (`DNI-OPN-1`, `KHR-OPN-4`) | нічне вікно проходить | — |
| Overlap | інша `APPROVED`/`UNDER_REVIEW` заявка на те саме ПС | `TSD-4 §5` |

Ключові сценарії curfew (`06` §1.4):
- вікно повністю поза curfew → PASS;
- вікно, яке починається до curfew і закінчується в ньому (напр. `LVV-RST-2`, 21:30–22:30 місцевого) → FAIL. Вікно, обидва кінці якого поза curfew, а середина в ньому, при межі тривалості 240 хв можливе тільки для дуже коротких curfew. У каталозі таких немає, тому «minute-by-minute» перевіряється саме через вікна, що частково заходять у curfew;
- curfew через північ як один безперервний період (вікно 01:00–02:00 місцевого → FAIL);
- `KBP-CTR-3` 22:00–22:59 місцевого → PASS (бо `A-7`), а для `LVV-RST-2` те саме → FAIL. Це регресія поправки `A-7`;
- межа curfew (вікно закінчується рівно о 23:00 / починається рівно о 05:00) → **Q-16**.

Ключові сценарії overlap (`06` §1.4, `02`):
- накладення з `UNDER_REVIEW` → FAIL; з `APPROVED` → FAIL;
- накладення з `DRAFT`, `REJECTED`, `CANCELLED`, `COMPLETED` → PASS;
- суміжні вікна (14:00 кінець / 14:00 початок) → PASS;
- те саме вікно, **інше** ПС → PASS;
- `validate` пройшов, потім інша заявка на це ПС стала `UNDER_REVIEW`/`APPROVED`, після чого `submit` → FAIL (очікувана поведінка за `02`);
- код відповіді для overlap: `422 TIME_WINDOW` (`06`) чи `409` «scheduling conflict» (`03`) → **Q-04**.

Орієнтовно: 30–35 ТК.

### TA-11. Конвеєр гейтів: порядок, `validate` vs `submit`, тіло `422` — P1

Джерела: `03` Gate pipeline, endpoint 13, The 422 body; `06` Evaluation order.

- Порядок `PILOT → AIRCRAFT → ZONE → TIME_WINDOW`; при кількох провалах повертається **лише перший** (комбінації: PILOT+ZONE, AIRCRAFT+TIME_WINDOW, ZONE+TIME_WINDOW, усі чотири).
- Кожна `422` містить `failing_gate`, `rule_reference`, `message`. `rule_reference` дослівно з `06` §6, ніколи не `TSD-4 §3.2` (ілюстративний приклад).
- `message` зрозумілий оператору і специфічний для причини (якісна перевірка, P3).
- `validate` **не змінює стан**: стан, `submitted_at`, `failing_gate` і `AuditLog` до і після виклику однакові; повторні виклики безпечні.
- `validate` і `submit` на тих самих даних дають однаковий результат гейтів.
- `validate` у будь-якому стані заявки (DRAFT, UNDER_REVIEW, REJECTED…): поведінка не описана → **Q-17**.
- Формат відповіді `validate`: «per-gate pass/fail» і «all four gate results» (`04`) проти «stopping at the first failure» (`03`) → **Q-01**.
- Після gate-відхилення через `submit` у заявці збережені `failing_gate`, `rejection_reason`, `rule_reference` (`01`, міграція 0002).

Орієнтовно: 15–18 ТК.

### TA-12. Стан-машина — P1

Джерела: `02` повністю; `03` endpoints 10, 14, 15, 16.

- Повна матриця 6.1: кожна легальна пара → цільовий стан; кожна нелегальна пара → `409`.
- `SUBMITTED` ніколи не спостерігається «в спокої» після `submit` (`GET` одразу після відповіді показує `UNDER_REVIEW` або `REJECTED`).
- Дедлайн скасування `APPROVED`: > 2 год до `window_start` → `CANCELLED`; < 2 год → `409` (не `422`). Точна межа в 2 год → **Q-18**.
- `COMPLETED` не виставляється автоматично з плином часу: `APPROVED` заявка з `window_end` у минулому залишається `APPROVED`. Через lead time ≥ 6 год це потребує очікування або підготовки даних.
- `APPROVED → COMPLETED` через maintenance endpoint → **BLOCKED** (**Q-02**: ендпоінта немає в контракті).
- `SUBMITTED → CANCELLED` мануально не відтворюється (вікно між submit і рішенням гейтів синхронне) → **BLOCKED / not testable manually**, фіксуємо як обмеження.

Орієнтовно: 35–40 ТК (у тому числі 25+ нелегальних пар).

### TA-13. Рішення reviewer — P1

Джерела: `02`; `03` endpoints 15, 16; `01` ReviewAction, FlightRequest; `04` Reviewer queue.

- Approve `UNDER_REVIEW` → `APPROVED`; створюється `ReviewAction(action=APPROVE, reviewer_id = значення хедера)`; `decided_at`, `decided_by` заповнені.
- Reject з `note` → `REJECTED`; `ReviewAction(action=REJECT, note)`.
- Reject без `note` / з порожньою `note` → відхилено. Код (`400`?) не названий явно → **Q-13**.
- Approve/reject не з `UNDER_REVIEW` → `409`.
- Подвійний approve (повторний клік, дві вкладки) → другий `409`, другий `ReviewAction` не створюється.
- Які поля заповнюються при відхиленні reviewer-ом (`failing_gate`? `rejection_reason` = note?) → **Q-05**.
- Чи перезапускаються гейти/overlap на approve → **Q-19**.

Орієнтовно: 12–15 ТК.

### TA-14. Списки і фільтри заявок — P2

Джерела: `03` endpoint 12; `04` My requests, Reviewer queue.

- Оператор: «My requests» фільтрується за станом (усі 7 значень + без фільтра).
- API: фільтри `state`, `zone_code`, діапазон дат, і їхні комбінації. За яким полем рахується діапазон дат, не описано → **Q-20**.
- Reviewer: список по всіх операторах, фільтр `operator_id`.
- Reviewer queue показує лише `UNDER_REVIEW` і сортується за часом сабміту (в обидва боки).
- Після approve/reject заявка зникає з черги.

Орієнтовно: 12–15 ТК.

### TA-15. Аудит (`AuditLog`, `ReviewAction`) — P2

Джерела: `01` AuditLog; `02` Implementation note.

- Кожен перехід стану створює рядок `AuditLog` з `entity_type="FlightRequest"`, `from_state`, `to_state`, `actor`, `created_at`.
- Подія створення має `from_state = null`.
- Для `submit` невідомо, чи логуються два переходи (DRAFT→SUBMITTED і SUBMITTED→UNDER_REVIEW/REJECTED) чи один → **Q-21**.
- `validate` і відхилені `409` спроби не створюють рядків.
- У API і UI немає жодного шляху update/delete для `AuditLog` (перевірка відсутності: перебір методів PUT/PATCH/DELETE по можливих шляхах, UI).
- Перевірка йде через read-only доступ до БД тестового середовища: у продукті немає ендпоінта читання аудиту.

Орієнтовно: 8–10 ТК.

### TA-16. UI: Operator portal і Reviewer queue — P2

Джерела: `04` повністю.

- Перемикач ролей у хедері; reviewer вводить `X-Reviewer-Id` у хедері UI (не логін).
- Сторінки: `/login`, `/register`, реєстр пілотів, реєстр ПС, форма заявки, «My requests», деталі заявки.
- Кнопка «Check before submitting» показує результат по гейтах і не змінює стан (перевірити, що стан у списку/деталях не змінився).
- Деталі заявки показують `rejection_reason` і `rule_reference` для відхилених заявок, і після перезавантаження сторінки теж (значення збережені, `01` rule_reference).
- Reviewer: деталі заявки з усіма чотирма результатами гейтів (див. **Q-01**); reject без note не відправляється.
- Доступ незалогіненого користувача до сторінок operator portal: поведінка (редирект?) не описана → **Q-22**.
- Відображення часу в UI (UTC чи місцевий) → **Q-14**.

Орієнтовно: 20–25 ТК.

### TA-17. Контракт `data-testid` — P3

Джерела: `04` Two contracts to hold exactly.

- Кожен інтерактивний елемент обох порталів має непорожній `data-testid` (інвентаризація через DevTools).
- Значення унікальні в межах сторінки й стабільні між перезавантаженнями та ролями.
- Обов'язкові названі значення: `operator-login-link`, `operator-register-link`, `operator-session-info`, `operator-logout-button`; приклад `flight-request-submit-button`.
- Повного реєстру значень у docs немає → **Q-23**. Пропонується зафіксувати фактичний список як baseline для R1.

Орієнтовно: 5–8 ТК + чекліст.

### TA-18. Оператор `SUSPENDED` — BLOCKED

Джерела: `05` row 4, §1; `07` п. 3.

- Відомо: це передумова для create/submit/approve, **не** гейт. Відповідь **не** повинна бути `422` з `failing_gate`. Це можна перевірити вже зараз як негативну вимогу.
- Невідомо: статус-код і тіло відповіді. Позитивні очікувані результати **не** складаються до закриття питання. `403` з ad hoc тілом — лише placeholder (`05` §1), а не очікуваний результат.
- Невирішено також, що означає «approve» для suspended-оператора (заявка цього оператора, яку схвалює reviewer).

Орієнтовно: 4–6 ТК, усі зі статусом BLOCKED, крім перевірки «не `422`/не `failing_gate`».

### TA-19. Загальна валідація і помилки — P2/P3

Джерела: `03` Error semantics.

- Неправильний JSON, відсутні обов'язкові поля, неправильні типи, невідомі enum-значення → `400` з деталями валідації.
- Неіснуючі сутності → `404` (pilot, aircraft, operator, zone, flight-request).
- Заявка з неіснуючим `zone_code`/`pilot_id`/`aircraft_id` (`404` чи `400`) → **Q-13**.
- Висота ≤ 0 або дробова → не описано → **Q-24**.

Орієнтовно: 12–15 ТК.

## 6. Ключові матриці та межові значення

### 6.1 Стан-машина: стан × дія

Легенда: ✅ легальний перехід (цільовий стан); `409` нелегально; **B** заблоковано; **N/T** мануально не відтворюється.

| From \ Action | submit | approve | reject | cancel | complete |
|---|---|---|---|---|---|
| `DRAFT` | ✅ `UNDER_REVIEW` / `REJECTED` | `409` | `409` | ✅ `CANCELLED` | `409` / **B** (Q-02) |
| `SUBMITTED` | N/T | N/T | N/T | ✅ `CANCELLED` — N/T | N/T |
| `UNDER_REVIEW` | `409` | ✅ `APPROVED` | ✅ `REJECTED` | ✅ `CANCELLED` | `409` / **B** |
| `APPROVED` | `409` | `409` | `409` | ✅ `CANCELLED` (> 2 год) / `409` (< 2 год) | ✅ `COMPLETED` — **B** |
| `REJECTED` | `409` | `409` | `409` | `409` | `409` / **B** |
| `CANCELLED` | `409` | `409` | `409` | `409` | `409` / **B** |
| `COMPLETED` | **B** | **B** | **B** | **B** | **B** |

Джерело: `02` таблиця переходів. Стан `COMPLETED` недосяжний, поки не визначено maintenance endpoint (Q-02). Комірки `complete` позначені B, бо шлях і авторизацію ендпоінта невідомо.

### 6.2 `PILOT`: рейтинг × клас зони (`OH-1 §2.1`)

| Рейтинг | `OPEN` (`DNI-OPN-1`, `KHR-OPN-4`) | `CONTROLLED` (`KBP-CTR-3`, `ODS-CTR-5`) | `RESTRICTED` (`LVV-RST-2`, `ZTM-RST-7`) |
|---|---|---|---|
| `R_BASIC` | PASS | FAIL | FAIL |
| `R_ADVANCED` | PASS | PASS | FAIL |
| `R_BVLOS` | PASS | PASS | PASS |

Currency (`OH-1 §2.3`), перевіряється на `window_start`:

| Випадок | Очікуване |
|---|---|
| `certified_on` = `window_start` − 17 міс. | PASS |
| `window_start` у межах 18 міс., день перед спливанням | PASS |
| `window_start` через 1 день після 18 міс. | FAIL («one day past is not current») |
| `window_start` рівно в день 18-місячної дати | **Q-03** (включно чи ні) |
| чинний на момент submit, сплив до `window_start` | FAIL |
| `certified_on` = `window_start` − 20 міс. (між 18 і 24) | FAIL (регресія проти v1.4) |
| `certified_on` у майбутньому | **Q-24** |

### 6.3 `AIRCRAFT`: межі ваги та категорії (`OH-1 §3`, `ZC-2026.1 §2`)

| `mtom_grams` | Категорія | `KBP`/`ODS` (C0–C2) | `LVV-RST-2` (C0–C1) | `ZTM-RST-7` (C0) | `DNI`/`KHR` (C0–C3) |

| 0 / 1 | C0 | PASS | PASS | PASS | PASS |
| 900 | C0 | PASS | PASS | PASS | PASS |
| 901 | C1 | PASS | PASS | FAIL | PASS |
| 3 500 | C1 | PASS | PASS | FAIL | PASS |
| 3 501 | C2 | PASS | FAIL | FAIL | PASS |
| 4 000 | C2 (регресія v1.4) | PASS | FAIL | FAIL | PASS |
| 12 000 | C2 | PASS | FAIL | FAIL | PASS |
| 12 001 | C3 | FAIL | FAIL | FAIL | PASS |
| 30 000 | C3 | FAIL | FAIL | FAIL | PASS |
| 30 001 | — | реєстрацію відхилено: `422`, `OH-1 §3` | | | |

FAIL у цій таблиці завжди означає `failing_gate: AIRCRAFT`, а не `ZONE`. Межі `0` і від'ємна маса не описані (Q-24).

### 6.4 `ZONE`: рівень авторизації оператора × вимога зони (`OH-1 §4`)

| Рівень оператора | `L1`-зони (`DNI`, `KHR`) | `L2`-зони (`KBP`, `ODS`) | `L3`-зони (`LVV`, `ZTM`) |
|---|---|---|---|
| `L1` | PASS | FAIL | FAIL |
| `L2` | PASS | PASS | FAIL |

Для перевірки `CONTROLLED`/`RESTRICTED` зон потрібні оператори `L2`/`L3`, а підвищити рівень можна тільки out-of-band (див. розділ 7).

Висота (`ZC-2026.1 §2`):

| Зона | Стеля | PASS | FAIL |
|---|---|---|---|
| `KBP-CTR-3`, `DNI-OPN-1`, `KHR-OPN-4` | 120 | 120 | 121 |
| `ODS-CTR-5` | 90 | 90 | 91 |
| `LVV-RST-2` | 60 | 60 | 61 |
| `ZTM-RST-7` | 45 | 45 | 46 |

### 6.5 `TIME_WINDOW`: межі

| Параметр | PASS | FAIL | Джерело |
|---|---|---|---|
| Lead time | ≈ 6 год + запас; 6 год рівно (≥) — з урахуванням обмеження 4.4 | 5 год 59 хв | `TSD-4 §2.1` |
| Advance booking | 60 днів (≤) мінус запас | 60 днів + 1 хв / 61 день | `TSD-4 §2.2` |
| Тривалість | 15 хв, 240 хв | 14 хв, 241 хв, 0 хв, від'ємна | `TSD-4 §3` |
| Curfew `KBP`/`ODS` | 22:00–22:59 місц., 05:00–06:00 місц. | 23:00–23:15 місц., 04:30–05:00 місц. | `A-7 §1` |
| Curfew `LVV`/`ZTM` | 06:00–07:00 місц., 21:00–21:45 місц. | 21:45–22:15 місц., 05:45–06:15 місц., 01:00–02:00 місц. | `ZC-2026.1 §3` |
| Overlap | суміжні вікна; інше ПС; конфлікт тільки з DRAFT/REJECTED/CANCELLED/COMPLETED | спільна хвилина з UNDER_REVIEW/APPROVED | `TSD-4 §5` |

Точне трактування меж curfew (чи вікно 22:00–23:00 для `KBP` дотикається до curfew, чи заходить у нього) див. Q-16.

### 6.6 Скасування `APPROVED` (`TSD-4 §6`)

| До `window_start` | Очікуване |
|---|---|
| ≥ 3 год | `CANCELLED` |
| 2 год + запас | `CANCELLED` |
| рівно 2 год | **Q-18** |
| < 2 год (напр. 1 год 50 хв) | `409` |

Щоб отримати APPROVED заявку менше ніж за 2 год до старту, потрібно або чекати (lead time ≥ 6 год), або підготувати дані в БД тестового середовища.

## 7. Тестове середовище та дані

### 7.1 Середовище

- Окремий **тестовий** інстанс SkyPermit із застосованими міграціями `0001`–`0004` і `seed.sql`. Готує команда розробки. QA не запускає нічого в `../skypermit` і не звертається до його Supabase (`CLAUDE.md`).
- Read-only доступ до БД тестового інстансу: для `AuditLog`, `ReviewAction` і полів, яких немає в API.
- Канал для out-of-band змін даних, які виконує адміністратор/розробник за запитом QA: зміна `authorisation_level`, `Operator.status`, `Pilot.status`, `Aircraft.status`, `Zone.active`, зсув часу заявок.
- Браузери: остання стабільна версія Chrome (основний) і Firefox (вибірково, P2).
- Синхронізований годинник тестувальника (UTC), калькулятор часових поясів для curfew.

### 7.2 Набір тестових даних

| ID | Дані | Як отримати |
|---|---|---|
| `OP-L1-A`, `OP-L1-B` | два оператори `L1`, для тестів ізоляції | реєстрація через UI/API |
| `OP-L2` | оператор `L2` | реєстрація + out-of-band підвищення |
| `OP-L3` | оператор `L3` | реєстрація + out-of-band підвищення |
| `OP-SUSP` | оператор `SUSPENDED` | out-of-band (для TA-18, BLOCKED) |
| `PIL-BASIC/ADV/BVLOS` | по одному пілоту кожного рейтингу з чинною currency, у `OP-L3` і `OP-L1-A` | API |
| `PIL-EXPIRING` | пілот, у якого 18 міс. спливають між «зараз + 6 год» і «зараз + 60 днів» | API, `certified_on` розраховується від дати прогону |
| `PIL-EXPIRED` | `certified_on` > 18 міс. тому; також 20 міс. (регресія v1.4) | API |
| `PIL-INACTIVE` | `INACTIVE` пілот | out-of-band |
| `AC-<маса>` | ПС з масами з 6.3 (900, 901, 3 500, 3 501, 4 000, 12 000, 12 001, 30 000) | API |
| `AC-RETIRED` | `RETIRED` ПС | out-of-band |
| `ZONE-INACTIVE` | одна зона з `active=false` (тимчасово, з відкатом) | out-of-band, **після** погодження, бо це довідник |
| Reviewer ids | `rev-qa-1`, `rev-qa-2` | значення хедера |

Унікальні поля (`email`, `national_id`, `serial_number`) генеруються з префіксом прогону, щоб уникнути колізій між прогонами.

## 8. Критерії входу, призупинення та виходу

### 8.1 Критерії входу

- Збірка R1 розгорнута на тестовому середовищі; міграції й seed застосовані; `GET /zones` повертає 6 зон.
- Smoke (1 щасливий шлях DRAFT → UNDER_REVIEW → APPROVED + провал кожного з 4 гейтів) пройдено.
- Підготовлено тестові дані з 7.2 (принаймні оператори `L1`/`L2`/`L3`).
- Тест-кейси P1 написані та переглянуті.

### 8.2 Критерії призупинення

- Не працює логін або реєстрація (блокує все operator-scoped тестування).
- `submit` або `validate` повертає `5xx` для валідних даних.
- `validate` змінює стан заявки (порушення ключового контракту, `03` endpoint 13).
- Оператор бачить або змінює дані іншого оператора (критичний дефект безпеки).

Відновлення: після фіксу і повторного smoke.

### 8.3 Критерії виходу (готовність до релізу)

- 100 % ТК P1 виконано; 0 відкритих дефектів Critical/High у P1-областях.
- ≥ 95 % ТК P2 виконано; відкриті дефекти Medium мають погоджений план або прийняті власником продукту.
- Усі BLOCKED/NEEDS-CLARIFICATION ТК мають явне рішення: питання закрите і ТК виконано, або ризик прийнято і задокументовано (зокрема Q-02 і TA-18).
- Регресія P1 після останнього фіксу пройдена.
- Звіт про тестування з покриттям за TA, дефектами і переліком відкритих питань передано власнику продукту.

## 9. Відкриті питання та прогалини в документації

Пункти Q-xx не мають очікуваного результату в цьому плані. Відповідні ТК позначаються **BLOCKED** (немає функціональності/контракту) або **NEEDS-CLARIFICATION** (поведінка є, але не визначена в docs). Нічого не виправляється в `../skypermit`, усе фіксується тут.

## 10. Дефекти та звітність

- Дефект містить: TA/ТК, кроки, фактичний і очікуваний результат **з посиланням на docs** (файл + розділ), запит/відповідь API або скріншот, середовище, збірку.
- Severity: **Critical** (втрата/витік даних між операторами, неправильне рішення гейта, `validate` змінює стан), **High** (неправильний перехід стану, неправильний `rule_reference`/`failing_gate`, неправильний статус-код у P1), **Medium** (фільтри, UI-відображення, аудит), **Low** (тексти, `data-testid`, косметика).
- Розбіжність docs і продукту, коли docs мовчать або суперечать собі, оформлюється не як дефект, а як питання Q-xx у цьому репозиторії.
- Щоденний статус: виконано / пройдено / провалено / заблоковано за TA. Фінальний звіт за критеріями 8.3.

| Ризик | Ймовірність / вплив | Пом'якшення |
