## 1. Мета

1–3 речення: що цей план має гарантувати і для якого рішення (реліз, регрес, приймання фічі).

## 2. Обсяг

### 2.1 В обсязі
Список областей (з префіксами `AREA` з `coverage-areas.md`) та ендпоінтів/сторінок.

### 2.2 Поза обсягом
Що свідомо не тестується і чому (напр. автотести, продуктивність, редагування зон — немає API).

## 3. Об'єкт тестування

Коротко: які сутності, стани, ендпоінти, сторінки зачіпає план. Без переказу docs — посилання.

## 4. Підхід

- Рівні/типи: функціональне API (мануально, напр. через REST-клієнт), UI, наскрізні сценарії.
- Техніки тест-дизайну і де саме застосовуються (state transition, BVA, EP, decision table, pairwise, negative).
- Як перевіряються побічні ефекти (стан заявки, `AuditLog`, `ReviewAction`).

## 6. Тестові дані

Таблиці з конкретними значеннями: зони (з каталогу), оператори з рівнями `L1`–`L3`, пілоти з кожним рейтингом і датами `certified_on` для меж currency, дрони з масами на межах бендів (±1 г), часові вікна для меж lead time / advance / duration / curfew / cancellation deadline. Вказуй, які дані неможливо створити через продукт (напр. `L2`/`L3`, неактивна зона) і потребують підготовки.
